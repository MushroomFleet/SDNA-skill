Self-Describing Data Architecture

The File Carries
Its Own DNA

Struct DNA — Generalised Methodology

The data you write today will be read by a version of your software that does not exist yet. SDNA is a five-principle methodology distilled from Blender's legendary file format — the system that lets a file saved in 1999 open perfectly in 2026.

The Core Problem

Why Data Formats Break

Every conventional approach to data versioning has a fatal weakness. SDNA's answer is architecturally different: embed the schema in the data itself, then reconcile on load.

❌ Anti-pattern
Fixed Binary Schemas
Break silently the moment any struct changes. A single added field shifts every byte offset downstream.
❌ Anti-pattern
Version Numbers Only
Require exhaustive migration code for every version pair. O(N²) complexity as versions accumulate.
❌ Anti-pattern
External Schema Registries
Create external dependencies. Registries rot, go offline, or diverge from the actual data in production.
❌ Anti-pattern
Human-Readable (JSON/XML)
Verbose and slow — and still break when field names change or structural semantics shift across versions.
❌ Anti-pattern
"Never Change the Schema"
Impossible at any meaningful scale. Requirements change. Optimisations require restructuring. Features evolve.
✓ SDNA Answer
Embed the Schema in the Data
The artifact carries its own blueprint. The reader discovers layout at load time rather than assuming it at compile time. Reconcile on load.
Methodology

The Five Principles

Each principle addresses a specific failure mode in data format evolution. Click any principle to expand the implementation pattern and anti-pattern.

1
Self-Description
The artifact carries its own schema; the reader discovers layout, it does not assume it
▶

Every persisted data artifact carries a complete description of its own structure — what named fields exist, what type each field is, what the size and shape of arrays and references are. This description is written at save time, not read time.

✓ Implementation Pattern
Embed a compact schema block alongside your data. The schema block is always written first on save and always parsed first on load. The reader builds a field map from the artifact itself before touching any data.
✗ Anti-Pattern
Assuming the reader shares the writer's compiled struct definitions. This is only safe within a single binary release — the moment versions diverge, silent corruption begins.
2
Name-Based Field Mapping
Fields are matched by name across versions, never by byte offset or positional index
▶

When the reader reconciles its current schema against the artifact's embedded schema, it resolves fields by symbolic name. Fields can be reordered freely. New fields get safe defaults. Removed fields are skipped cleanly. Fields present in both are mapped directly.

✓ Implementation Pattern
Store field names as strings (or interned string IDs) in the schema block. The loader iterates the artifact's field list and resolves each by name lookup — not positional assumption.
✗ Anti-Pattern
Positional/index-based deserialisation: "field 3 is always the Y coordinate." A single insertion anywhere breaks everything downstream — every field after the insertion reads wrong data.
3
Incremental Versioning Patches
Migrations are a chain of small, ordered, permanent patch functions
▶

Name-based mapping handles easy cases. But deep structural changes — a scalar becoming an array, degrees becoming radians, a nested struct flattened — require active data transformation. These are expressed as a permanent, ordered chain of patch functions applied from the artifact's version to the current one.

✓ Implementation Pattern
Monotonically increasing version integer. A registry of patch functions indexed by version. On load, apply patches from artifact_version to current_version in sequence. Patches accumulate — never collapse or remove.
✗ Anti-Pattern
A single migrate(from, to, data) function with a large switch statement. Becomes unmaintainable. Also: collapsing old patches into a "legacy" path — removes the ability to load any artifact older than the collapse point.
4
Graceful Degradation
Unknown blocks and fields are skipped cleanly; partial reads are valid
▶

When an older reader encounters a newer artifact, it will find blocks and fields it has no knowledge of. The correct behaviour: skip unknown blocks entirely, skip unknown fields within known structs using embedded schema sizes, and load what is understood. This property must be designed in — it is not automatic.

✓ Implementation Pattern
Every block stores its own byte length in the header — unknown blocks skippable in O(1). Field sizes come from the embedded schema, so unknown fields can also be skipped safely without knowing their content.
✗ Anti-Pattern
Treating an unknown block type as a fatal error. This makes every new writer a breaking change for every old reader — an enormous compatibility tax paid forward in perpetuity.
5
Two-Layer Architecture
Storage schema and public interface schema are separated by a stable mapping layer
▶

Blender calls these DNA (storage) and RNA (interface). The storage schema evolves freely to match implementation needs. The public interface schema evolves conservatively to preserve compatibility for consumers. A mapping layer translates between them — internal refactors never break the public API.

✓ Implementation Pattern
Artifact → (SDNA load + patches) → Internal representation (evolves freely) → (stable mapping layer) → Public API (evolves conservatively). Consumers always see the stable layer, never the storage structs.
✗ Anti-Pattern
Exposing internal storage structs directly as the public API. Any internal change — renaming a field, splitting a struct, changing a type — immediately becomes a breaking change for every consumer.

Applications

Where SDNA Applies

Any system that persists structured data across software versions is a candidate. The higher the data's expected lifetime or the broader its reader ecosystem, the more SDNA compliance is worth.

🎮
Game Save Files
Save games written at v1.0 must remain playable at v2.5. Player data structures evolve with every patch cycle.
🗄️
Database Schemas
Migrations that run forward-only leave older clients unable to read new records. Self-description enables bidirectional tolerance.
🌐
Network Protocols
Clients and servers rarely update in lockstep. Graceful degradation means a v3 client can still talk to a v5 server without crashing.
📦
Asset Pipelines
3D models, textures, and scene files are authored in one tool and consumed by another. Schema drift between tools causes silent data loss.
⚙️
Configuration Formats
Config files outlive the software versions that wrote them. Self-description prevents "unknown key" errors as features are added and removed.
🔬
Scientific Data Archives
Research data may be accessed decades after it is written. The schema must travel with the data — the original software is long gone.
